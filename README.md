# TU Basket Booking

ระบบจองสนามบาสเกตบอลของคณะวิทยาศาสตร์และเทคโนโลยี มหาวิทยาลัยธรรมศาสตร์ ศูนย์รังสิต
เป็นโปรเจกต์วิชา CS261 ของกลุ่ม 1

นักศึกษาเข้ามาเลือกวัน เลือกสนาม แล้วจองช่วงเวลาที่ว่างได้เลย ส่วนเจ้าหน้าที่ที่ประตูสนาม
ก็ค้นหาการจองด้วยรหัสจองแล้วกดเช็คอินให้ได้ทันที

## ตอนนี้ทำอะไรได้บ้าง

### Sprint 1: จองสนามและเช็คอินพื้นฐาน

- **จองสนาม** เลือกวันได้ล่วงหน้าไม่เกิน 7 วัน สนามเปิด 08:00 – 19:00 จองได้คนละไม่เกิน 2 ชั่วโมงต่อวัน
  ช่วงไหนมีคนจองแล้วหรือเลยเวลาไปแล้วจะกดไม่ได้
- **ประวัติการจอง** ดูการจองทั้งหมดของตัวเอง พร้อมสถานะ (รอเช็คอิน, เช็คอินแล้ว, ยกเลิกแล้ว, ไม่มาเช็คอิน)
- **เช็คอินโดยเจ้าหน้าที่** ค้นหาด้วยรหัสจอง แล้วกดยืนยัน เช็คอินได้ตั้งแต่ 15 นาทีก่อนเวลาเริ่ม
  ถึง 15 นาทีหลังเวลาเริ่ม ถ้าเลยจากนั้นระบบจะเปลี่ยนเป็น "ไม่มาเช็คอิน" และคืนช่องเวลาให้คนอื่นจองต่อ

### Sprint 2: Login, สิทธิ์การใช้งาน, QR Code และยกเลิกการจอง

- **เข้าสู่ระบบด้วยบัญชี TU** นักศึกษาใช้ Username/Password เดียวกับระบบมหาวิทยาลัย
  ระบบส่งไปตรวจกับ TU API แล้วสร้าง session ให้ ไม่ต้องส่งรหัสนักศึกษามากับทุก request อีกต่อไป
  ยังไม่ได้ login จะถูกพาไปหน้า login ก่อน และ login เสร็จจะกลับมาหน้าเดิม
- **บัญชีเจ้าหน้าที่สนาม** เจ้าหน้าที่มีบัญชีและรหัสผ่านของระบบเอง (ไม่ใช่บัญชี TU) login จากแท็บ "เจ้าหน้าที่"
  แล้วเข้าหน้าเช็คอินทันที ส่วน API `/api/staff/*` ใช้ได้เฉพาะ role `staff` เท่านั้น
- **จำกัดสิทธิ์จองเฉพาะคณะวิทยาศาสตร์และเทคโนโลยี** ระบบตรวจคณะจาก session ตอนจอง
  นักศึกษาคณะอื่นจะได้ `403 FACULTY_NOT_ALLOWED`
- **QR Code สำหรับเช็คอิน** หน้าประวัติแสดง QR Code ของการจองที่ยังรอเช็คอิน
  เจ้าหน้าที่เปิดหน้าสแกนแล้วส่องกล้องได้เลย ระบบตรวจลายเซ็นของ QR ก่อน แล้วพาไปหน้ายืนยันเช็คอิน
  (การค้นหาด้วยรหัสจองแบบ Sprint 1 ยังใช้ได้เหมือนเดิม)
- **ยกเลิกการจอง** กดยกเลิกจากหน้าประวัติได้ จนถึง 1 ชั่วโมงก่อนเวลาเริ่ม ช่องเวลาจะว่างให้คนอื่นจองต่อทันที
- **หน้าเว็บตามดีไซน์ใหม่** ปรับหน้าจอง ประวัติ เช็คอิน และ login ให้ตรงกับดีไซน์ มีแถบเมนูบนเดสก์ท็อป
  และป๊อปอัปโปรไฟล์
- **Docker แยก 3 container** frontend (nginx), backend (FastAPI) และ db (MySQL) แยกกัน
  รายละเอียดดูที่ [วิธีรันด้วย Docker](#วิธีรันด้วย-docker-แนะนำ)

เบื้องหลังของแต่ละอย่างอธิบายไว้ใน [Sprint 2 ทำงานอย่างไร](#sprint-2-ทำงานอย่างไร)

## เทคโนโลยีที่ใช้

| ส่วน | ใช้อะไร |
|---|---|
| หน้าเว็บ | HTML, CSS, JavaScript ธรรมดา (ไม่มี framework) |
| Backend | Python + FastAPI + SQLAlchemy |
| ฐานข้อมูล | MySQL 8.4 (ตอนรันด้วย Docker) หรือ SQLite (ตอนรันบนเครื่องตัวเอง) |

### เวอร์ชัน Python

- **ใน Docker** ใช้ **Python 3.12** (image `python:3.12-slim`) ไม่ต้องลง Python เองเลย
- **รันบนเครื่องตัวเอง** ต้องเป็น **Python 3.10 ขึ้นไป** (ทีมลองกับ 3.13 แล้วใช้ได้)
  เช็คเวอร์ชันได้ด้วย `python3 --version` (Windows ใช้ `py --version`)

## วิธีรันด้วย Docker (แนะนำ)

วิธีนี้ง่ายสุด ไม่ต้องลง Python หรือ MySQL เอง ระบบแยกเป็น 3 container

| Container | หน้าที่ | พอร์ตบนเครื่อง |
|---|---|---|
| `frontend` | nginx เสิร์ฟหน้าเว็บ (HTML/CSS/JS/รูป) และส่งต่อ `/api` ไปที่ backend | `3000` |
| `backend` | FastAPI (API อย่างเดียว ไม่มีไฟล์หน้าเว็บ) | `8000` |
| `db` | MySQL 8.4 | `3308` |

หน้าเว็บเรียก `/api` ผ่าน origin เดียวกับหน้าเว็บ (พอร์ต 3000) nginx จะส่งต่อไปที่ container `backend`
cookie ของ session หลัง login จึงใช้ได้โดยไม่ต้องตั้งค่า CORS เพิ่ม

**1. เปิด Docker Desktop** แล้วรอจนขึ้นว่า running

**2. สร้างไฟล์ `.env`** จากไฟล์ตัวอย่าง (ทำแค่ครั้งแรกครั้งเดียว)

```bash
cp .env.example .env
```

ถ้าใช้ Windows (PowerShell) ให้ใช้ `Copy-Item .env.example .env` แทน

จากนั้นเปิดไฟล์ `.env` แล้วกำหนดค่ารหัสผ่านและ secrets รวมถึง TU API Application Key

```text
DB_PASSWORD=รหัสผ่านฐานข้อมูล
DB_ROOT_PASSWORD=รหัสผ่าน root ของฐานข้อมูล
QR_HMAC_SECRET=ข้อความลับยาวๆ อะไรก็ได้
TU_API_APPLICATION_KEY=Application-Key ที่ได้รับจาก TU API
```

เก็บ `TU_API_APPLICATION_KEY` และ secrets ไว้ฝั่ง Backend เท่านั้น อย่าใส่ใน JavaScript
หรือ commit ค่าใช้งานจริงขึ้น Git

`SESSION_SECRET` ใช้เซ็น session ที่สร้างหลัง login สำเร็จ (ต้องตั้งค่า ไม่อย่างนั้น API จะไม่เริ่มทำงาน)
และ `SESSION_TIMEOUT_MINUTES` กำหนดว่า session อยู่ได้กี่นาที (ค่าเริ่มต้น 60)

`STUDENT_REGISTRY_PROVIDER=mock` ใช้คณะจากข้อมูล login ของ TU ในการตรวจสิทธิ์จอง
(ถ้าไม่ได้ตั้งค่านี้ใน `.env` การจองจะได้ `503 STUDENT_REGISTRY_UNAVAILABLE`)

**3. สั่งให้ทุกอย่างทำงาน**

```bash
docker compose up -d --build
```

ครั้งแรกจะช้าหน่อยเพราะต้องโหลด image รอสักพักก็เสร็จ

**4. เปิดเว็บได้เลย**

| หน้า | ลิงก์ |
|---|---|
| หน้าเว็บ (เข้าสู่ระบบ / จองสนาม) | <http://localhost:3000> |
| ประวัติการจอง | <http://localhost:3000/html/history.html> |
| หน้าเช็คอินของเจ้าหน้าที่ | <http://localhost:3000/html/check-in-scan.html> |
| เอกสาร API | <http://localhost:3000/docs> (หรือ <http://localhost:8000/docs>) |

คำสั่งอื่นที่ใช้บ่อย

```bash
docker compose ps                 # ดูว่า frontend, backend, db ทำงานอยู่ไหม
docker compose logs -f backend    # ดู log ของ backend
docker compose logs -f frontend   # ดู log ของ nginx
docker compose down               # ปิดระบบ (ข้อมูลการจองยังอยู่)
docker compose down -v            # ปิดระบบและล้างข้อมูลในฐานข้อมูลทิ้งทั้งหมด
```

ถ้าแก้โค้ดต้องรัน `docker compose up -d --build` ใหม่ทุกครั้ง เพราะไฟล์ถูกก๊อปไปไว้ใน image แล้ว
(แก้แค่หน้าเว็บใช้ `docker compose up -d --build frontend` ก็พอ)

อยากเปิดดูข้อมูลในฐานข้อมูลด้วย DBeaver ก็เชื่อมไปที่ `127.0.0.1` พอร์ต `3308`
ใช้ชื่อผู้ใช้ `booking_user` กับรหัสผ่าน `DB_PASSWORD` ใน `.env`

### ดูฐานข้อมูลด้วย phpMyAdmin

phpMyAdmin เป็นเครื่องมือเสริม ไม่ได้เป็นส่วนหนึ่งของระบบ จึงไม่ถูกเปิดพร้อม `docker compose up`
ถ้าต้องการใช้ ให้รันคำสั่งนี้จากโฟลเดอร์โปรเจกต์ แล้วเข้าที่ <http://localhost:8080>

```bash
docker compose --profile tools up -d phpmyadmin
```

ในหน้าเข้าสู่ระบบ ใช้ข้อมูลดังนี้

| ช่อง | ค่า |
|---|---|
| Server | `db` |
| Username | `root` |
| Password | ค่า `DB_ROOT_PASSWORD` ในไฟล์ `.env` |

หลังเข้าสู่ระบบ เลือกฐานข้อมูล `tu_basket_booking` เพื่อดูตารางและข้อมูลได้
อย่าเปิดเผย phpMyAdmin ออกสู่อินเทอร์เน็ต เพราะเป็นเครื่องมือจัดการฐานข้อมูลโดยตรง

## วิธีรันบนเครื่องตัวเอง (ไม่ใช้ Docker)

ใช้ SQLite แทน MySQL ข้อมูลจะเก็บอยู่ในไฟล์ `dev.db` ในโฟลเดอร์โปรเจกต์ เหมาะกับการลองเล่นหรือเขียนโค้ด

**ครั้งแรก:** สร้าง virtual environment แล้วลงแพ็กเกจ

macOS / Linux

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
```

Windows (PowerShell)

```powershell
py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements-dev.txt
```

**ทุกครั้งที่จะรัน:** เปิด venv แล้วสั่งเปิด server

macOS / Linux

```bash
source .venv/bin/activate
DATABASE_URL=sqlite:///./dev.db QR_HMAC_SECRET=dev-secret TU_API_APPLICATION_KEY=ใส่คีย์ที่ได้รับ uvicorn app.main:app --port 8000
```

Windows (PowerShell)

```powershell
.\.venv\Scripts\Activate.ps1
$env:DATABASE_URL = "sqlite:///./dev.db"
$env:QR_HMAC_SECRET = "dev-secret"
$env:TU_API_APPLICATION_KEY = "ใส่คีย์ที่ได้รับ"
uvicorn app.main:app --port 8000
```

เห็นคำว่า `Uvicorn running on http://127.0.0.1:8000` แปลว่าพร้อมแล้ว เปิดลิงก์เดียวกับในตารางข้างบนได้เลย
อย่าปิดหน้าต่าง Terminal นี้ระหว่างใช้งาน กด `Ctrl+C` เมื่ออยากปิด

อยากล้างการจองทั้งหมดแล้วเริ่มใหม่ ก็ปิด server แล้วลบไฟล์ `dev.db` ทิ้งได้เลย

> **ข้อควรระวัง:** ต้องเปิดหน้าเว็บผ่าน `http://localhost:8000/...` เท่านั้น
> ถ้าดับเบิลคลิกเปิดไฟล์ HTML ตรงๆ หน้าเว็บจะคุยกับ backend ไม่ได้

## ข้อมูลตัวอย่างและผู้ใช้ทดสอบ

ตอนเปิด server ระบบจะใส่ข้อมูลตัวอย่างให้เอง (อิงจากวันที่ปัจจุบัน) มีสนาม 2 สนาม
นักศึกษาจาก 3 คณะ และบัญชีเจ้าหน้าที่ 2 บัญชี

| ผู้ใช้ | บทบาท | รหัสผ่าน |
|---|---|---|
| `A` | นักศึกษา | อะไรก็ได้ (เฉพาะตอนยังไม่มี TU API Key) |
| `B` | นักศึกษาอีกคน มีการจองไว้แล้วบางช่วง | อะไรก็ได้ (เฉพาะตอนยังไม่มี TU API Key) |
| `C` | นักศึกษาคณะวิศวกรรมศาสตร์ | อะไรก็ได้ (เฉพาะตอนยังไม่มี TU API Key) |
| `D` | นักศึกษาคณะศิลปศาสตร์ | อะไรก็ได้ (เฉพาะตอนยังไม่มี TU API Key) |
| `S` | เจ้าหน้าที่ | `staff1234` (login ที่แท็บเจ้าหน้าที่ ใช้ได้ตลอด) |
| `S2` | เจ้าหน้าที่ทดสอบอีกบัญชี | `staff1234` (login ที่แท็บเจ้าหน้าที่ ใช้ได้ตลอด) |

API ที่ต้องรู้ว่าใครใช้งาน (จองสนาม ประวัติ ฯลฯ) ระบุผู้ใช้จาก session ที่ได้หลัง
`POST /api/auth/login` สำเร็จ ไม่ได้ใช้ header `X-Student-Id` แล้ว
ถ้ายังไม่ได้ login จะได้ 401 และหน้าเว็บจะพาไปหน้า `html/login.html` ให้ก่อน
login เสร็จแล้วจะกลับมาหน้าเดิม

### Login ด้วยผู้ใช้ทดสอบ (ระหว่างยังไม่มี TU API Key)

ถ้ายังไม่ได้ใส่ `TU_API_APPLICATION_KEY` ใน `.env` แท็บนักศึกษาจะ login ด้วยบัญชีทดสอบให้แทน
พิมพ์ชื่อผู้ใช้ตามตารางข้างบน เช่น `A` รหัสผ่านใส่อะไรก็ได้
(เบื้องหลังคือ `POST /api/auth/dev-login`) ส่วนเจ้าหน้าที่ใช้รหัสผ่านจริงเสมอ ดูหัวข้อถัดไป

- ใช้ได้เฉพาะผู้ใช้ที่มีอยู่ในฐานข้อมูลแล้ว และเฉพาะตอน `APP_ENV` ไม่ใช่ `production`
- พอใส่ `TU_API_APPLICATION_KEY` แล้ว ระบบจะปิดทางนี้เองและใช้ login ผ่าน TU จริงทันที
  ไม่ต้องแก้โค้ด

คำสั่ง `python -m app.scripts.migrate` สร้างตารางและใส่ข้อมูลตัวอย่างด้วยเมื่อเปิด
`AUTO_SEED` (ค่าเริ่มต้นใน development) หากเป็น production หรือปิด `AUTO_SEED`
คำสั่งนี้จะสร้างเฉพาะตาราง ไม่ใส่บัญชีทดสอบ

ถ้าเป็นเครื่องที่ใช้งานจริง ให้ตั้ง `APP_ENV=production` และ `AUTO_SEED=false` ข้อมูลตัวอย่างจะได้ไม่ถูกใส่เข้าไป

### บัญชีเจ้าหน้าที่สนาม (login ด้วยรหัสผ่านของระบบ ไม่ใช่ TU)

เจ้าหน้าที่สนามอาจไม่มีบัญชี TU จึง login ที่แท็บ **เจ้าหน้าที่สนาม** ด้วยชื่อผู้ใช้และรหัสผ่านของระบบนี้
(`POST /api/auth/staff-login`) หลัง login จะไปที่หน้าสแกน QR เช็คอิน

**ใช้บัญชีทดสอบได้เลย:** ชื่อผู้ใช้ `S` หรือ `S2` รหัสผ่าน `staff1234`
ใช้ได้ทั้งตอนที่มีและไม่มี TU API Key ไม่ต้องสร้างบัญชีเอง

- รหัสผ่านนี้ถูกใส่มาพร้อมข้อมูลตัวอย่าง (`AUTO_SEED`) ซึ่งเปิดเฉพาะตอน development
  เครื่องที่ใช้งานจริง (`AUTO_SEED=false`) จะไม่มีบัญชีนี้
- ถ้าฐานข้อมูลเดิมสร้างไว้ก่อนแล้ว รัน `docker compose up -d --build` ใหม่หนึ่งครั้ง
  ระบบจะเติมรหัสผ่านให้ `S` และ `S2` ตอนเปิด backend

อยากสร้างบัญชีเจ้าหน้าที่ใหม่ หรือเปลี่ยนรหัสผ่าน (เช่น `S`) ใช้คำสั่งนี้
ระบบจะถามรหัสผ่าน (อย่างน้อย 8 ตัวอักษร) โดยไม่แสดงบนจอ และเก็บแค่ค่า hash (scrypt) ในตาราง `staff_credentials`

```bash
docker compose exec backend python -m app.scripts.create_staff S
docker compose exec backend python -m app.scripts.create_staff staff01 --name "ชื่อเจ้าหน้าที่"
```

- รันซ้ำกับชื่อเดิมเพื่อเปลี่ยนรหัสผ่าน รหัสผ่านที่ตั้งเองจะไม่ถูกเปลี่ยนกลับเป็น `staff1234` ตอนเปิดระบบใหม่
- ใช้ชื่อของบัญชีนักศึกษา (role `member`) ไม่ได้ ระบบไม่เปลี่ยนนักศึกษาเป็นเจ้าหน้าที่ให้
- บัญชี TU ที่ชื่อผู้ใช้ซ้ำกับบัญชีเจ้าหน้าที่จะ login แทนไม่ได้ (ได้ `409 USE_STAFF_LOGIN`)

## Login ผ่าน TU API

`POST /api/auth/login` รับ `username` และ `password` แล้วส่งไปตรวจสอบกับ TU API ที่
`https://restapi.tu.ac.th/api/v1/auth/Ad/verify` โดยส่ง Application Key จาก
`TU_API_APPLICATION_KEY` ใน header ฝั่ง server เท่านั้น ระบบไม่เก็บรหัสผ่าน TU
และบันทึกหรืออัปเดตข้อมูลผู้ใช้ที่ตรวจสอบสำเร็จในตาราง `users` โดยใช้ `username`
จาก response ของ TU เป็นรหัสนักศึกษา/ผู้ใช้

ตัวอย่าง API:

```http
POST /api/auth/login
Content-Type: application/json

{"username":"รหัส TU","password":"รหัสผ่าน TU"}
```

เมื่อสำเร็จ API ตอบข้อมูลที่บันทึกแล้ว เช่น

```json
{
  "studentId": "6601000001",
  "name": "นักศึกษาทดสอบ",
  "faculty": "คณะทดสอบ"
}
```

ถ้า TU ปฏิเสธ Username/Password จะตอบ `401 INVALID_CREDENTIALS`; ถ้า TU
เชื่อมต่อไม่ได้จะตอบ `503 TU_API_UNAVAILABLE` หรือ `504 TU_API_TIMEOUT`
พร้อมข้อความ “ไม่สามารถเชื่อมต่อระบบยืนยันตัวตนของมหาวิทยาลัยได้ กรุณาลองใหม่อีกครั้งภายหลัง”
กรณี Application-Key หรือ body ที่ส่งไป TU ผิด จะได้ `TU_API_KEY_UNAUTHORIZED`,
`TU_API_KEY_FORBIDDEN` หรือ `TU_API_REQUEST_ERROR` เพื่อแยกจาก credentials ของผู้ใช้
กำหนด `TU_API_TIMEOUT_SECONDS` ได้ตั้งแต่ 5 ถึง 10 วินาที (ค่าเริ่มต้น 10 วินาที)
เมื่อ login สำเร็จ API จะตั้ง cookie `tu_basket_session` ให้ด้วย (ดูหัวข้อ
[Session หลัง login](#1-session-หลัง-login)) API อื่นๆ จะรู้ว่าใครใช้งานจาก cookie นี้

สำหรับบัญชีพนักงาน TU ส่ง `organization` แทน `faculty`; เนื่องจากตาราง `users`
ยังไม่มีช่อง organization ระบบจึงไม่บันทึก organization เป็นคณะ และใช้ค่า
`มหาวิทยาลัยธรรมศาสตร์` ในช่อง faculty แทน

ขณะนี้เอกสาร TU API ที่ส่งมามีข้อมูลพอสำหรับขั้นตอนนี้แล้ว หากจะต่อยอดในภายหลัง
ควรยืนยันเพิ่มว่า endpoint นี้อนุญาตทั้งบัญชีนักศึกษาและพนักงานหรือไม่ และค่า
`username` ใน response เป็นรหัสที่ต้องใช้เป็น key ในระบบอย่างสม่ำเสมอหรือไม่

## โหมดเดโม: ขยายเวลาเช็คอิน

ปกติเช็คอินได้แค่ 15 นาทีก่อนและหลังเวลาเริ่ม ซึ่งเวลาพรีเซนต์ในห้องเรียนอาจรอไม่ไหว
เลยมีค่า `CHECKIN_WINDOW_MINUTES` ไว้ขยายช่วงนี้ เช่นตั้งเป็น `4320` (72 ชั่วโมง)

```bash
# รันบนเครื่องตัวเอง
CHECKIN_WINDOW_MINUTES=4320 DATABASE_URL=sqlite:///./dev.db QR_HMAC_SECRET=dev-secret uvicorn app.main:app --port 8000

# รันด้วย Docker
CHECKIN_WINDOW_MINUTES=4320 docker compose up -d
```

ค่านี้ใช้เฉพาะรอบที่สั่งรันเท่านั้น รอบหน้าถ้าไม่ได้ใส่ ระบบก็กลับไปใช้กฎ 15 นาทีตามปกติ

## Sprint 2 ทำงานอย่างไร

### 1. Session หลัง login

- login สำเร็จ (ทั้งแบบ TU และเจ้าหน้าที่) backend จะตั้ง cookie `tu_basket_session`
  ข้างในเป็นรหัสผู้ใช้กับเวลาหมดอายุ เซ็นด้วย HMAC จาก `SESSION_SECRET` ใครแก้ cookie เองจะใช้ไม่ได้
- cookie เป็น `HttpOnly` และ `SameSite=Lax` JavaScript ในหน้าเว็บอ่านไม่ได้
  และอยู่ได้ตาม `SESSION_TIMEOUT_MINUTES` (ค่าเริ่มต้น 60 นาที)
- หน้าเว็บเรียก API ผ่าน `js/api.js` ซึ่งส่ง cookie ไปทุกครั้ง ถ้าได้ `401` จะพาไปหน้า login
  พร้อมจำหน้าเดิมไว้ใน `?next=` login เสร็จก็กลับมาหน้าเดิม
- ใน Docker หน้าเว็บกับ API อยู่ origin เดียวกัน (`localhost:3000` ผ่าน nginx) cookie จึงใช้ได้โดยไม่ต้องตั้ง CORS

### 2. บัญชีเจ้าหน้าที่

- ข้อมูลเจ้าหน้าที่อยู่ในตาราง `users` (role `staff`) ส่วนรหัสผ่านอยู่ในตาราง `staff_credentials`
- รหัสผ่าน hash ด้วย scrypt พร้อม salt สุ่ม (ไลบรารีมาตรฐานของ Python) ไม่เก็บรหัสผ่านจริง
- บัญชีทดสอบ `S` และ `S2` ได้รหัสผ่าน `staff1234` มาพร้อมข้อมูลตัวอย่าง
- สร้างหรือเปลี่ยนรหัสผ่านด้วย `python -m app.scripts.create_staff` (ดูหัวข้อบัญชีเจ้าหน้าที่ด้านบน)
- แท็บเจ้าหน้าที่ไม่มี login ทดสอบ ต้องใช้รหัสผ่านจริงเสมอ ไม่ว่าจะใส่ TU API Key หรือยัง
- หน้า login มีสองแท็บ แท็บนักศึกษาเรียก `/api/auth/login` แท็บเจ้าหน้าที่เรียก `/api/auth/staff-login`
  login เสร็จระบบเช็ค role จาก `/api/auth/me` ถ้าเป็นเจ้าหน้าที่จะไปหน้าเช็คอินเสมอ

### 3. ตรวจสิทธิ์ตามคณะ

1. ก่อนจอง ดูประวัติ หรือยกเลิกการจอง หน้าเว็บจะเรียก `POST /api/session/start` หนึ่งครั้ง
2. backend ดึงรายชื่อคณะของนักศึกษาจาก student registry แล้วเก็บไว้ในตาราง
   `student_faculty_sessions` และ `student_faculty_memberships`
3. ตอนจอง `POST /api/bookings` ตรวจว่ามี `คณะวิทยาศาสตร์และเทคโนโลยี` อยู่ในรายชื่อนั้นไหม
   ถ้าไม่มีได้ `403 FACULTY_NOT_ALLOWED` ถ้ายังไม่ได้ดึงข้อมูลคณะได้ `409 STUDENT_SESSION_REQUIRED`

ตอนนี้ student registry ของจริงยังไม่มี จึงใช้ `STUDENT_REGISTRY_PROVIDER=mock`
ซึ่งใช้คณะจากข้อมูล login ของ TU ถ้าอยากลองกรณีนักศึกษาหลายคณะ ใส่ JSON ใน `STUDENT_REGISTRY_MOCK_DATA` ได้ เช่น

```text
STUDENT_REGISTRY_MOCK_DATA={"6601000001":["คณะวิศวกรรมศาสตร์","คณะวิทยาศาสตร์และเทคโนโลยี"]}
```

ลองกับผู้ใช้ทดสอบได้เลย `A` จองได้ ส่วน `C` (วิศวกรรมศาสตร์) และ `D` (ศิลปศาสตร์) จะจองไม่ได้

### 4. QR Code สำหรับเช็คอิน

```text
นักศึกษา (หน้าประวัติ)                      เจ้าหน้าที่ (หน้าสแกน)
GET /api/bookings/{code}/qr  ──►  รูป QR  ──►  กล้องอ่าน QR (jsQR)
                                                   │
                                     POST /api/staff/qr/scan  → ตรวจ QR และแสดงรายละเอียดการจอง
                                                   │
                        POST /api/staff/bookings/{code}/checkin  → ยืนยันเช็คอิน
```

- ใน QR คือข้อความ `<รหัสจอง>.<ลายเซ็น>` เช่น `TU-69101201.3f9a...`
  ลายเซ็นเป็น HMAC-SHA256 ของรหัสจองด้วย `QR_HMAC_SECRET` ซึ่งรู้แค่ฝั่ง server
  จึงปลอม QR หรือแก้รหัสจองใน QR ไม่ได้
- ระบบตรวจลายเซ็นก่อนอ่านฐานข้อมูล QR ปลอมจะได้ `400 INVALID_QR` โดยไม่บอกว่ารหัสจองนั้นมีอยู่จริงไหม
- QR แสดงได้เฉพาะการจองของตัวเองที่ยังรอเช็คอิน และตอบกลับด้วย `Cache-Control: no-store`
  เพราะ QR ใช้เหมือนตั๋ว
- การจองที่ยกเลิกแล้ว เช็คอินแล้ว หรือไม่มาเช็คอิน สแกนแล้วจะไปหน้า "เช็คอินไม่ได้" พร้อมเหตุผล
- กล้องต้องเปิดผ่าน `localhost` หรือ HTTPS เท่านั้น (ข้อกำหนดของเบราว์เซอร์)

### 5. ยกเลิกการจอง

- ยกเลิกได้เฉพาะการจองของตัวเองที่ยังรอเช็คอิน และต้องเหลือเวลาอย่างน้อย 1 ชั่วโมงก่อนเริ่ม
  ไม่อย่างนั้นได้ `422 CANCEL_TOO_LATE`
- ยกเลิกแล้วสถานะเป็น "ยกเลิกแล้ว" บันทึกเวลาที่ยกเลิก และคืนช่องเวลาให้คนอื่นจองได้ทันที
- ชั่วโมงที่ยกเลิกไม่นับในโควตา 2 ชั่วโมงต่อวัน จองใหม่ได้

| ตัวแปร | ใช้ทำอะไร |
|---|---|
| `TU_API_APPLICATION_KEY` | Application Key ของ TU API (ถ้าว่าง จะใช้ login ทดสอบแทน) |
| `TU_API_TIMEOUT_SECONDS` | เวลารอ TU API 5 – 10 วินาที (ค่าเริ่มต้น 10) |
| `SESSION_SECRET` | ใช้เซ็น session cookie ต้องตั้งค่า |

| `STUDENT_REGISTRY_PROVIDER` | แหล่งข้อมูลคณะ ตอนนี้รองรับแค่ `mock` |
| `STUDENT_REGISTRY_MOCK_DATA` | (ไม่บังคับ) JSON กำหนดคณะของนักศึกษาแต่ละคน |

## เจอปัญหา ลองดูตรงนี้ก่อน

| อาการ | วิธีแก้ |
|---|---|
| ขึ้นกล่องแดงว่า **เชื่อมต่อเซิร์ฟเวอร์ไม่ได้** | server ยังไม่ได้เปิด หรือปิดไปแล้ว ลองเปิดใหม่ |
| `address already in use` | มี server อีกตัวเปิดอยู่ที่พอร์ต 8000 แล้ว ปิดตัวเก่าก่อน (`Ctrl+C` หรือ `docker compose down`) |
| `command not found: uvicorn` หรือ `No module named ...` | ลืมเปิด venv ให้รัน `source .venv/bin/activate` ก่อน |
| Docker ขึ้นว่า `Set DB_PASSWORD in .env` | ยังไม่ได้สร้างไฟล์ `.env` ดูขั้นตอนที่ 2 ของ Docker |
| วันนี้ทุกช่องขึ้น **หมดเวลา** | เลยเวลาไปแล้ว (สนามปิด 19:00) ลองเลือกวันถัดไป |
| จองหรือเปิดประวัติแล้วขึ้น **ตรวจสอบข้อมูลคณะไม่ได้** (`503 STUDENT_REGISTRY_UNAVAILABLE`) | ยังไม่ได้ใส่ `STUDENT_REGISTRY_PROVIDER=mock` ใน `.env` ใส่แล้วรัน `docker compose up -d` ใหม่ |
| หน้าสแกน QR ไม่เปิดกล้อง | ต้องเปิดผ่าน `localhost` หรือ HTTPS และกดอนุญาตให้เบราว์เซอร์ใช้กล้อง ถ้ายังไม่ได้ก็ค้นหาด้วยรหัสจองแทน |
| (Mac) สั่ง `pytest` หรือเปิด server แล้วค้างเฉยๆ ไม่ขึ้นอะไรเลย | ถ้าโปรเจกต์อยู่ใน Desktop/Documents ที่ซิงก์กับ iCloud ไฟล์อาจถูกย้ายไปเก็บบนคลาวด์ ทางแก้ที่ดีสุดคือย้ายโปรเจกต์ไปไว้ที่อื่น เช่น `~/Projects` หรือสร้าง venv ชื่อ `.venv.nosync` แล้วทำลิงก์ `ln -s .venv.nosync .venv` (iCloud จะไม่ยุ่งกับโฟลเดอร์ที่ลงท้ายด้วย `.nosync`) |
